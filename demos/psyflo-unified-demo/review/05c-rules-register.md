# 05c · Rules register (policy, deadline, unit and regulatory rules in the demos and docs)

Companion to `05-safety-and-data-integrity.md`. Every rule that appears in either demo, the seed, or the project documents is listed once, with the value the code uses today, a source category, and a proposed row for the configurable rules table the build will add (Part 4.6).

## Categories

| Category | Meaning | UI chip |
|---|---|---|
| OFFICIAL-VERIFIED | In a DMAS manual, Virginia Administrative Code text or an official DMAS form, **as read by the evidence agent in Harvest's Drive copies** (T-068 to T-075). I did not re-open the primary sources; currency of the 7/1/2022 manual revision is unchecked. | "Official · <doc> · verified <date>" |
| PAYER-SPECIFIC | Written payer or contractor guidance, channels, or a requirement stated by the payer in a message. | "Payer guidance · <payer>" |
| HARVEST-REPORTED | Said by Harvest staff or observed on site; no regulation or payer document found. | "Harvest practice" |
| UNVERIFIED-DEMO-ASSUMPTION | PsyFlo-written secondary compilation, a product design rule, or a number the demo invented. Rules tagged *design rule* are PsyFlo's own product choices, not regulatory claims. | "Demo assumption · unverified" |

v3's four tags map directly: `policy` and `documented` → OFFICIAL-VERIFIED; `observed` → HARVEST-REPORTED; `unverified` → UNVERIFIED-DEMO-ASSUMPTION (`02-core-data.js:66-96`). v3's rule rows (`id, area, service, payers, kind, text, source, verified`) are the right shape to adopt.

## Proposed table schema (one row per rule)

`key` · `value` · `unit` · `scope` (service line, payer, document) · `category` · `source_doc` · `source_cite` · `verified_by` · `verified_on` · `effective_from` · `effective_to` · `display_text` · `override_by_request` (true where a payer message states its own deadline) · `last_changed_by`. Changes are audited and apply forward only. The UI shows the chip and source wherever a rule drives a date, a unit count or a claim.
