Existing master: `web/screens/Analytics.dc.html` + controller.

Build (`#/Analytics?section=outcomes|payer|population&dataset=case|illustrative`):
1. **Pure selectors** `web/js/shared/analytics/{casebacked,cohort,metrics,export,pdf-report}.js`: every selector returns `{rows, provenance:'case_backed'|'harvest_export'|'illustrative', asOf, source}`; one dataset per view with a banner chip; no sums across datasets; `harvest_export` is labelled "Sample data, illustrative"; the 120-patient v3 cohort is generated deterministically client-side (not stored in state; ids `COH-…`, initials hidden); minimum group size 5 enforced inside the selectors (smaller groups show "Fewer than 5"); patient-level drill-down only for case-backed rows and the `analytics.drilldown` capability (admin gets aggregates only). `metrics.js` defines each pilot measure once (numerator, denominator, source, definition string shown on demand).
2. **Pilot scorecard** (first band in Analytics, case-backed): the six measures of `02` §g (notes completed in the agreed window, time preparing documentation, intake-complete → review-ready SRA, missing items caught before processing, submissions with receipts, unresolved payer requests), computed from stored notes, requests, events; the figures must MOVE when a note is processed or an authorization is sent or a decision is recorded (scenario S6); definitions behind a "?" popover; "Future" chip on long-term payer approval metrics.
3. **Patient Outcomes**: patients with usable outcome data, goals and progress (from stored goals and notes), assessment trends only where scores exist (never fabricated), behavioral and school functioning, feedback and **Treatment Feedback & Engagement** (the former FIT section; not a separate tab), data completeness, patients needing clinical review; keep progress, intervention exposure and outcomes distinguishable and print no causal claims.
4. **Payer Performance**: requests submitted, approved vs requested units, partial decisions, denials, turnaround (Day N), reauthorization burden, common payer reasons, upcoming payer work; case-backed first, the seeded baseline labelled; payer rows open `#/DenialCase` / the queue filtered; a payer guidance drawer from E3's `payer-guidance.js` (use it if present; otherwise a link).
5. **Patient Population**: enrollment, age groups, schools/localities, diagnoses, co-occurring, service types, treatment goals, documented interventions, utilization, admissions/discharges; diagnosis ≠ treatment goal ≠ intervention ≠ service type (separate groupings); contextual drill-downs; dataset toggle (case-backed vs illustrative cohort) with the banner.
6. **Reporting**: filters via `filterBar` (date range, site, payer, program); a question box that answers only from the data actually available (rule-based; label "Simulated"), unsupported questions return an understandable limitation; exports (CSV and PDF) carrying period, filters, definitions and provenance, matching the screen; grant-pull counts computed or labelled (the old constants 52/14/3 go).
7. The old Analytics content that is not in the unified design stays reachable (an "Earlier views" drawer) so nothing is silently removed; PayerPlaybook content is reached via the payer section.
8. Notes `seed/notes/e4.md`.

Done when: all three sections render for admin, clinician (own caseload) and supervisor (own site) with the right limits; no figure mixes datasets (`test/analytics.mjs`: provenance tags, min-n, no blending, permission-gated drill-down, figures move after actions); export file matches the screen; smoke; screenshots 1440/1024; density within the 03b targets.
